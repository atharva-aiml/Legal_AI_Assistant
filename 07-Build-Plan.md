# Build Plan — Legal AI Assistant

Traces to [02-Requirements.md](02-Requirements.md) and [05-System-Architecture.md](05-System-Architecture.md). This is a living document — as a version finishes, flip its `Status` line to `Done` and record the date in place; don't regenerate this file from scratch. Each version is a vertical slice: the domain rule, its DB table(s), its API endpoint(s), and its real UI are built together, not as separate "backend sprint" / "frontend sprint" passes.

**Backend migration note (2026-08-14):** V0.1 and V0.2 were originally built with the backend inside Next.js (API routes + Drizzle). Per explicit user request, the backend was then split by language — Java (Spring Boot) for all CRUD/"rest of the backend," Python (FastAPI) for AI, Next.js reduced to UI-only — with no functionality change, verified via full regression (Technology Decision Log). Every "API" reference in the version descriptions below now means the Java backend (`/backend-java`) unless the version is AI-specific (V0.3/V0.4, Python). Repo layout is `/frontend`, `/backend-java`, `/backend-python`, `/database` — see CLAUDE.md §0.

## Version 0.3 — Document Upload & Ingestion

**Status:** Done — 2026-08-14
**Service split:** upload endpoint + `Document` row CRUD is Java (SD-002/SD-008); OCR → chunk → embed processing is Python (SD-004) — System Architecture §2's "shared database, two backend languages" note. Both point at the same local `uploads/` directory in dev (no R2 credentials available — System Architecture §6).

**Domain rule → repository → API → UI, together:**
- Domain rule: a Document belongs to exactly one Matter (BR-002); only PDF/DOCX/common image types are accepted (REQ-003); it becomes queryable only after processing succeeds (REQ-004).
- Repository: `Document` + `DocumentChunk` tables (`document_chunks.embedding` fixed at `vector(384)`).
- API: `POST /api/matters/:id/documents`, `GET /api/matters/:id/documents`, `GET /api/documents/:id`, `GET /api/documents/:id/download` (Java) — plus Python's `POST /ingest/:documentId`, called directly by Java (no queue yet — System Architecture §7).
- UI: Documents section inside Matter Detail, upload control with per-file status badge (Uploading/Processing/Ready/Failed) and an inline error message on failure.
- Ingestion pipeline (Python, SD-004): native text extraction for PDF (`pypdf`)/DOCX (`python-docx`), OCR for image uploads (EasyOCR), chunked **per real page**, sentence-boundary-aware (~2800 chars/~400 overlap, approximating AI Architecture §2's token-based sizing — rebuilt 2026-08-15, see the third real bug below), embedded (`all-MiniLM-L6-v2`, spiked for real — Technology Decision Log), written to `document_chunks`.

**Done (live action):** A lawyer opens a Matter, uploads a real PDF, watches its status move Uploading → Processing → Ready, and can click through to download the original file byte-for-byte.

Verified 2026-08-14: 27 Java tests + 10 Python tests pass (domain + application-layer, both against in-memory fakes). Live regression against the real 3-service stack: uploaded a real hand-built PDF containing actual lease text — Java stored it, fired the Python hand-off, Python extracted the exact text, chunked it, embedded it (confirmed `vector_dims = 384` directly in Postgres), and the Document reached `status='ready'` end to end with no manual intervention. Separately uploaded a real synthetic scanned-document image ("Notice of Hearing Docket 88213") to exercise the OCR path specifically — EasyOCR correctly extracted it, proving both extraction branches, not just the native-text one. Also verified: download returns byte-identical original file; an unsupported file type (`.exe`) is rejected with `400` before any storage I/O; a second real registered Firm gets `404` (not `403`) on both the Document detail and Matter-scoped Document list, proving BR-008 holds for Documents even though they carry no `firm_id` column directly (enforced via a join to `matters`).

**Known scope boundary, not a bug:** a *scanned* PDF (an image with no text layer, wrapped in a PDF container) isn't OCR'd in this version — `pypdf` returns empty text for it, which the pipeline correctly surfaces as a "failed" Document ("No extractable text found") rather than silently producing nothing. REQ-003's "scanned images" are supported as plain image uploads (PNG/JPEG/TIFF/WEBP); true scanned-PDF support would need a PDF-to-image rendering step not yet built.

**Real bug found by the user's own testing, fixed same day (2026-08-15):** uploading a genuine AES-encrypted PDF (a real TCS Provident Fund statement — common corporate-document protection, not a rare case) failed with `cryptography>=3.1 is required for AES algorithm`. The failure-handling itself worked correctly (caught, surfaced as `status='failed'` with a clear message, per §7's "no failure is invisible" rule) — the gap was a missing optional dependency. Added `cryptography` to `backend-python`, reproduced the failure against the user's actual uploaded file first, then confirmed the fix against that same real file end to end through the real `/ingest` endpoint (not a synthetic replacement) — Document moved to `status='ready'` with real extracted content and embeddings (Technology Decision Log).

**Addendum — Delete & Download Documents (REQ-027, 2026-08-15):** completes Document CRUD rather than warranting its own version. Download was already built (`GET /api/documents/:id/download`, V0.3) but never wired to the UI — just a frontend addition. Delete is new: `DELETE /api/documents/:id`, **unrestricted** (explicit user decision — not gated on Matter status, despite BR-007's "closed Matters never hard-deleted" language; that rule isn't reachable yet since Matter-closing (V0.5) doesn't exist). `document_chunks.document_id`'s FK gained `ON DELETE CASCADE` so removing a Document cleans up its embeddings at the DB level without Java touching Python-owned rows directly.

**Second real bug found by the user's own testing, fixed same day (2026-08-15):** a 60-page PDF upload appeared stuck on "Processing" for 5 minutes, resolving only on a manual tab refresh. Checked Postgres timestamps before touching any code: actual ingestion had finished in 7 seconds (56 real chunks/embeddings) — this was never a backend performance problem, it was the frontend never re-checking status after the initial page load (Next.js Server Component, fetch-once). Fixed with client-side polling (`documents-list.tsx`, 3s interval while anything is non-terminal). This is the project's first genuinely client-side-timing bug, so it's also the first thing that needed real browser verification instead of `curl` — set up Playwright (`/tests`, per CLAUDE.md's existing "eventually" commitment, now real) and wrote `document-status-polling.spec.ts`: uploads a real file, asserts the badge moves Processing → Ready with zero `page.reload()` calls in the test. Passed on the first real run.

**Third real bug found by the user's own use of the AI Assistant (V0.4), fixed 2026-08-15 — the ingestion pipeline itself was broken, not just the UI around it:** the user opened `document_chunks` in pgAdmin directly and reported five symptoms: `page_number` starting at 0; chunk `page_number=0` containing text from real pages 1–3; chunks breaking mid-word with no discernible pattern ("starts from `ues Clauses 7.2`..."); no visible criteria for where a chunk ends; and `page_number` topping out at 6 regardless of the document's actual page count. All five traced to three lines of code: `_extract_pdf` joined every page's text into one string *before* chunking (page boundaries lost entirely), `chunk_text()` sliced that blob by raw character offset with zero word/sentence awareness, and `save_chunks` stored the chunk's sequential index into the `page_number` column — so "page_number" never meant a real page at all, it meant "which chunk this was." Rebuilt as: extraction now returns each page's text separately (`ExtractedPage`, 1-indexed for PDF, `page_number=None` for DOCX — which has no page concept in the file itself, not a bug, a real format limitation — and `page_number=1` for single-pass OCR images); chunking now runs *per page* (a chunk can never span two real pages) and splits along sentence boundaries (paragraph breaks where the source has them, sentence-boundary regex otherwise, word-boundary hard-split only as a last resort for punctuation-free content like a table row), with overlap carried as whole trailing sentences instead of a raw character slice. Domain-tested alone first (10 new tests, including a direct repro of the "starts mid-word" symptom and a table-row hard-split case using an exact structure lifted from the real PDF the user attached), then re-verified end to end against that same real 11-page test PDF: `psql` confirms `page_number` running cleanly 1→11 with zero cross-page mixing and every chunk starting/ending on a real word; a live chat query about "Clause 7.2" returned a correctly-cited answer pointing at the exact page containing it (page 9, one of two genuine occurrences in the test document — not a fabricated number); a second query about the Financial Loss Ledger table correctly extracted a specific figure (₹185,000) with an accurate page-4 citation. Also caught and fixed a second, unrelated real bug during this pass's Playwright re-verification: `chat-panel.tsx`'s V0.4 readiness-polling fix scheduled only a single `setTimeout` rather than a repeating poll (it never re-armed itself the way `documents-list.tsx`'s polling does, because its `hasReadyDocuments` dependency doesn't change on a negative check) — made it self-perpetuate via a tick counter, confirmed with three consecutive clean Playwright runs after the fix.

## Version 0.4 — AI Assistant (Chat)

**Status:** Done — 2026-08-15
**Prerequisite resolved:** the LLM-provider spike (System Architecture §6, AI Architecture §2) — **OpenAI `gpt-4o-mini`**, chosen by explicit user decision after being asked directly (no default was assumed for an external paid API on a legal-data product). Real spike: a live call with a two-chunk grounded prompt produced correctly-cited output (`[1]`/`[2]` markers matching the right chunks) and correctly refused an unanswerable question in-context — before any pipeline code was written around it (Technology Decision Log).

**Service split:** Python owns the entire chat domain — retrieval, generation, grounding rules, `chat_messages`/`citations` persistence (SD-005). Java owns auth + Matter ownership (BR-008) and is a **synchronous** proxy to Python's internal `POST /chat/:matterId` / `GET /chat/:matterId` (not in the public API table, same trust boundary as V0.3's `/ingest/:documentId` — System Architecture §6's "Java ↔ Python hand-off" row, extended). This resolved a real ambiguity in System Architecture §1's diagram (which sketched the browser calling Python directly for chat) against SD-003's "Java is the sole authority on session validity" — the diagram was aspirational shorthand for the service boundary, not a literal call graph; Java-fronted was the only option that doesn't duplicate session verification into a second language.

**Domain rule → repository → API → UI, together:**
- Domain rule (Python, `app/domain/`): `retrieval.py` (Reciprocal Rank Fusion, AI Architecture §2), `chat.py` (BR-006 — an assistant answer needs ≥1 citation or must be the exact fixed not-found string), `citation_verification.py` (Grounding Rules 4/5 — strips any sentence lacking a citation marker that resolves to an actually-retrieved chunk). All three are pure functions/factories, unit-tested alone with no I/O (18 tests).
- Application (Python, `app/application/chat_service.py`): `ChatService.ask()` — the full pipeline (hybrid retrieval → RRF fusion → threshold gate → grounded generation → one corrective regeneration on an uncited answer → persistence), tested against in-memory fakes (9 tests) including the 422/502 failure paths.
- Repository: `chat_messages`, `citations` tables added to `/database`'s schema (`citations.document_id` is `ON DELETE SET NULL`, not `CASCADE` — a citation survives REQ-027's unrestricted Document delete as the historical record, per AI Architecture §4's "persisted permanently").
- API: Java's `GET /api/matters/:id/chat`, `POST /api/matters/:id/chat` (auth + BR-008 gated, proxies to Python) — `ChatService`/`ChatGateway`/`HttpChatGateway`, tested against an in-memory fake gateway (4 tests).
- UI: `chat-panel.tsx` inside Matter Detail — citations rendered as clickable links to the source Document's download endpoint, a soft low-confidence indicator, and (like V0.3's Documents tab) its own readiness polling — a Document that finishes ingesting after this page's first server render would otherwise show "Ready" in the Documents list while the Chat panel kept showing "Upload a document first" forever, the exact same staleness class as V0.3's bug, caught by the live Playwright check below, not by inspection.

**Real spike — retrieval thresholds (AI Architecture §2's other TBD, resolved here):** RRF fused-score floor `RELEVANCE_THRESHOLD = 0.01` (below this, the LLM is never called — Grounding Rule 2), `CONFIDENT_THRESHOLD = 0.02` (below this but above the floor, the answer is flagged low-confidence in the UI rather than blocked) — both against `k=60`. Spiked against a real uploaded lease document, not decided on paper; the spike also caught a real bug (next paragraph).

**Real bug found during the threshold spike, fixed same day:** `plainto_tsquery` ANDs every significant word in the question together — asking "how **long** is the lease term" against a chunk that says "the term is 36 months" (no literal word "long" anywhere) matched zero rows, even though "rent," "lease," and "term" all hit cleanly. Keyword search silently contributed nothing to fusion for any naturally-phrased question that included one word absent from the source text — not a rare case, closer to the common case. Fixed by reusing `plainto_tsquery`'s own stemming/stopword output but flipping its `&` to `|` in SQL (`to_tsquery('english', replace(plainto_tsquery(...)::text, ' & ', ' | '))`), rather than reimplementing tokenization in Python. Verified directly in `psql` before and after, then re-verified through the real pipeline.

**Verified 2026-08-15:** 32 Python tests + 34 Java tests pass (22 new Python tests and 4 new Java tests for this version, up from V0.3's 10 Python / 30 Java). Live regression against the real 3-service stack + real OpenAI API: uploaded a real multi-fact lease document (DOCX), asked "What is the monthly rent and how long is the lease term?" — got back a correctly-cited answer (`Rs. 1,45,000`, `36 months`, both `[1]`) pointing at the real Document with a real excerpt; asked an unrelated SEBI/insider-trading question — got back the exact fixed "I couldn't find that in this Matter's documents." with zero citations, not a fabricated answer. New Playwright tests (`chat.spec.ts`) prove both paths through a real browser, including that the conversation survives a `page.reload()` (real Postgres persistence, not React state) — caught and fixed the stale-props readiness bug above on the first real run.

**Second real bug found by the user's own use of the AI Assistant, fixed 2026-08-15 — after the chunking/page-number fix above, a related but distinct defect in the same bug family:** asking "Who is the client" returned a garbled fragment — `"Ltd. [1][2]."` — followed by the citation-verification gap note, instead of a real answer. Root cause: `citation_verification.py`'s sentence-splitting regex (punctuation + whitespace + capital letter = sentence boundary) misfired on **"Apex Components Pvt. Ltd."** the same way an earlier version had misfired on "Rs." — "Pvt." followed by "Ltd" (capitalized) looked like a sentence end, so the real sentence ("The client is Apex Components Pvt. Ltd. [1][2].") got split mid-name, detaching its citation marker from the first half and causing that half (plus, by the same cascading-offset mechanism, the explanatory sentence after it) to be dropped as "unsupported" under Grounding Rule 4 — leaving only the marker-bearing second half. Since `chunk.py` (ingestion) had independently built the near-identical regex and hit the near-identical "Rs." bug during V0.4's build, this was a duplicated-logic problem, not just a missing abbreviation: extracted a single shared `app/domain/sentence_split.py` with a real (if non-exhaustive) abbreviation list (`Pvt`, `Ltd`, `Mr`, `Dr`, `Rs`, `LLP`, month names, single initials, etc.), and pointed both `chunk.py` and `citation_verification.py` at it instead of maintaining two copies of the same bug class. 7 new domain tests, including the exact repro string. Live-verified against the real Apex Components matter already in Postgres (no re-upload needed — this bug lives entirely in chat-time answer verification, not ingestion): re-asked the exact reported question and got back `"The client is Apex Components Pvt. Ltd. [1][2]."` — complete, correctly cited, no gap note; a follow-up three-part question ("who is the client, who is the opposing party, and what are they claiming") returned three full clean sentences, each correctly citing entities containing "Pvt. Ltd." or "LLP," confirming the fix generalizes beyond the one-sentence case.

**Third real bug found by the user's own use of the AI Assistant, fixed 2026-08-15 — a broad question ("explain me the document") wrongly returned "not found" despite abundant relevant content:** direct diagnostic confirmed retrieval was healthy (8 real, relevant chunks, fused score well above threshold) — the LLM itself, given real context, chose to output the fixed not-found phrase. Root cause: the system prompt was validated only against narrow single-fact questions ("what is the rent"); it had no guidance for broad "explain/summarize" requests, and the model over-applied the "don't combine chunks into an unsupported conclusion" instruction to *any* multi-chunk synthesis, treating organizing real content across several chunks as too risky rather than distinguishing it from actually inferring something unstated. Rewrote `SYSTEM_PROMPT` to explicitly distinguish "restating/organizing what the chunks say" (always allowed, however broad the question) from "unsupported synthesis" (stating a legal conclusion, opinion, or inferred fact no chunk states — never allowed) — spiked iteratively against the real OpenAI API via a throwaway diagnostic script before committing to the wording, not decided on paper.

Fixing this surfaced a second, unrelated real bug in the same pass: `citation_verification.py` reconstructed the kept portion of an answer with `" ".join(kept_sentences)`, which flattened a long structured answer's markdown (numbered headings, bullets, blank lines between sections — exactly the format the user asked for, "good format") into a single space-joined wall of text. Traced to the shared `sentence_split.py` extracted for the previous bug: it discarded each sentence's original trailing whitespace on split. Fixed by having `split_into_sentences` retain each piece's original trailing separator, and `citation_verification.py` concatenate kept pieces directly (`"".join`) instead of re-joining with a single space — reconstruction of a fully-kept answer is now byte-for-byte identical to the source, and a partially-kept answer preserves the surviving sections' original formatting. 2 new domain tests for the formatting-preservation behavior specifically, plus the existing citation-verification suite (unaffected — its fixtures happened to already use single-space-separated sentences). Live-verified end to end: re-asked "explain me the apex meridian document" through the real API and got a detailed, well-formatted, correctly multi-cited explanation (numbered sections, bullets, 7 real citations across pages 2/3/6/7/9/10/11) instead of a refusal; re-confirmed the genuinely-unrelated SEBI question still correctly refuses (no regression in the anti-hallucination path).

**Open design question surfaced, not yet resolved — flagged to the user rather than decided unilaterally:** a generic scene-setting sentence with no specific citation (e.g. a broad answer's opening line, or a numbered list item that ends up entirely uncited) still gets dropped under Grounding Rule 4 and triggers the "some parts couldn't be verified" gap note, even when nothing factually wrong was removed — just stripped narration. Loosening this (e.g. exempting a single leading/trailing framing sentence from the citation requirement) is a real anti-hallucination-strictness tradeoff, not a clear-cut bug fix, so it wasn't changed without the user's input.

**Second open question, resolved by user decision — added a real metadata path, 2026-08-15:** "how many pages does the document have" answered "10 pages" (grounded in the document's own printed text, which says "Test Page N of 10" on every page) — but the real PDF has 11 physical pages; the fictional test document's own page-numbering is internally inconsistent (an authoring artifact, confirmed by inspecting the raw page text). Presented as a genuine product-scope question rather than deciding unilaterally: should the Assistant answer structural questions (page count, file name, document count) from real system metadata, distinct from grounded document-content answers? User chose yes. Built as: a new `document_metadata(matter_id)` repository method (`max(dc.page_number)` per ready Document — real DB fact, `NULL` for DOCX which has no page concept) is now always fetched and offered to the LLM as trailing numbered context items *after* the content chunks, clearly labeled "Document metadata," with the system prompt instructed to prefer metadata over a document's own self-description for structural questions. Reuses the exact same `[N]` citation-marker verification machinery as content chunks — a metadata-sourced citation just has `page_number=null` and a real, Python-computed (never LLM-authored) excerpt like `"apex_meridian_10_pages.pdf has 11 pages."`, keeping BR-006's "every claim needs a real citation or the fixed not-found response" guarantee intact for this new answer path too. Also handles the case where content retrieval finds nothing relevant at all (a purely structural question like "how many documents are in this Matter" might not match any chunk) — metadata is still tried via a metadata-only LLM call with zero document content in the prompt, preserving Grounding Rule 2's "no content shown to the LLM below threshold" guarantee for actual document content specifically. 6 new/updated tests (3 domain, 4 application-layer — one updated, three new, covering: below-threshold-with-metadata, below-threshold-with-metadata-still-refuses, and metadata-numbered-after-content-chunks). Live-verified: re-asked the exact reported question through the real API and got `"The document has 11 pages [9]."` — the real count, correctly cited to a real metadata fact (chunk items 1-8, metadata item 9); re-confirmed all three previously-fixed behaviors in this version (explain-the-document, the SEBI refusal, and the "who is the client" Pvt./Ltd. fix) still work with zero regressions.

**Major real-bug investigation and architecture change, 2026-08-16 — the user tested nine broad questions against a real 50-chunk/60-page test matter ("Sharma v. Meridian Buildtech"), and most came back thin, incomplete, or wrongly refused:** "explain this document" gave one narrow fact plus a gap note instead of an overview; "create a complete chronology" surfaced 2 of a real 9-entry chronology; "identify all important dates" also surfaced only 2; "give me a complete matter assessment" was decent but unstructured; "what are the strongest documents for the developer" said not-found outright. Investigated by reading the real document directly (not just the chat outputs), per the user's explicit ask to verify one answer ("contradictions regarding payment") against ground truth. Root cause: the document's real substance — parties, a 9-entry correspondence chronology, key financial figures, an Evidence Matrix, a Contradictions table — is concentrated on ~4 of its 60 pages, but `CONTEXT_SIZE=8`'s ranked top-8 selection cannot reliably surface even those few pages together against a vague broad query with no specific keywords to match ("create a complete chronology" doesn't semantically resemble the actual chronology text). Confirmed directly: the real "Key Correspondence" table (page 3) has almost exactly the chronology the user expected, but repeated chat answers only ever cited a narrow 1-2 page range — the fuller table simply never entered the LLM's context window.

Presented root cause + a 4-part plan to the user before building (matching this project's established practice for architecture-level changes), and got explicit sign-off including the real cost/latency tradeoff:

1. **Full-context path for small Matters (the core fix).** Below `FULL_CONTEXT_CHAR_CAP = 150,000` characters (~37K tokens — the real test matter measured only ~55K chars total, comfortably under), every Ready chunk is included directly instead of relying on RRF-ranked top-8; retrieval/RRF/the relevance-threshold gate only still apply once a Matter's real corpus exceeds that cap. New `all_ready_chunks(matter_id)` repository method, real SQL ordered by document/page for coherent reading. **Real, measured latency cost, reported honestly rather than hidden:** several full-context calls against the real test matter took 10–15.5s, over NFR-001's 8s p95 target (narrow single-fact questions on the same Matter stayed fast, 2–7s). This tradeoff was made deliberately with the user's sign-off in exchange for completeness on broad questions — not yet further optimized.
2. **Prompt tightened against cross-section conflation** — a real, only-partially-fixed precision issue caught during the required manual document check: one answer generalized a fact stated specifically about the *rent* ledger gap to "the claimed payments" broadly, implying doubt about the main (well-corroborated) payment figure that the source didn't actually support. Added an explicit "never generalize a fact from one topic to a different, related topic" instruction; re-tested and the conflation softened (more precise attribution, hedged language) but didn't fully disappear — reported as a real, ongoing LLM-precision limitation, not claimed as solved.
3. **Structured templates** for two recognizable broad-question types (matter overview → Client/Opposing Party/Forum; complete matter assessment → 7 ordered sections), layered on full cited detail. First version of the assessment template caused a real regression: a perfectly-written, fully-correct 7-section answer came back with **zero citation markers anywhere** (confirmed via a raw-LLM-output diagnostic script, bypassing citation verification to see what the model actually wrote), which correctly-behaving citation verification then collapsed entirely to the not-found response, since nothing had a marker to keep. Root cause: the template instruction told the model what sections to use without restating the citation requirement at that specific point — fixed by explicitly repeating "every fact under these headers still needs its own citation marker" right where the template is defined.
4. **A distinct `OUT_OF_SCOPE_RESPONSE`**, separate from `NOT_FOUND_RESPONSE`. Re-tested "strongest documents for the developer" *after* the full-context fix specifically (per the original plan's "re-test before assuming it needs scope-boundary handling") — it still returned not-found even with the entire document available, confirming this is a genuine Non-Goals scope boundary (legal-strategy judgment), not a retrieval gap. Added the second fixed response plus explicit prompt guidance distinguishing "topic not addressed" from "topic addressed, but requires a judgment only the lawyer can make."

**Verified 2026-08-16:** 63 Python tests pass (up from 50 — new tests for the full-context path, the large-corpus fallback forced via `monkeypatch` on `FULL_CONTEXT_CHAR_CAP`, and `OUT_OF_SCOPE_RESPONSE`), Java unaffected (no Java changes this pass), Playwright chat tests still pass. Live-verified all nine originally-reported questions against the real matter through the real internal chat endpoint: chronology went from 2/9 to 14/14 real dated events with proper citations; "all important dates" likewise reached 14/14 with no gap note; the matter-overview and matter-assessment questions now return the exact structured templates requested, fully cited; the out-of-scope question now gets the distinct message instead of a misleading "not found." Real latency measured and reported, not glossed over.

**Done (live action):** A lawyer opens a Matter with at least one Ready Document, asks a question whose answer is in that document, and gets back an answer with a citation that correctly points to that document and page; asking something not covered by the documents gets an explicit "I couldn't find that" response instead of a fabricated one.

## Version 0.5 — Deadlines, Notifications & Matter Closure

**Status:** Done — 2026-08-16

**Domain rule → repository → API → UI, together:**
- Domain rule (`domain/Deadline.java`): `create()` enforces BR-004 (matterId/title/dueDate required; `notificationLeadDays` defaults to 3 per REQ-009 if omitted, rejects negative); `isNotificationDueOn(today)` is REQ-009's pure reminder-timing rule; `openOnes(deadlines)` is BR-003's pure filter. `domain/Notification.java`: `create()` requires recipient/deadline/message. `domain/Matter.java` gained a `closedAt` field, closing a real pre-existing gap — the DB column and entity getter/setter already existed from V0.1/V0.2 but the domain record and its mapping never used them. 21 domain tests (`DeadlineTest`, `NotificationTest`).

**Real bug caught by my own testing before it reached a live check:** `NotificationScanServiceTest`'s idempotency test used a fixed simulated `today` for `scan(today)`, but the idempotency check compares against a Notification's real `createdAt` (`Instant.now()`), not the simulated date — so a repeat scan never saw a match and created a duplicate. ## Version 0.6 — Search

**Status:** Done — 2026-08-16

**Domain rule → repository → API → UI, together:**
- Domain rule (`domain/SearchQuery.java`): `parse(q, status, from, to)` validates raw request input — blank query is treated as "no query" (not an error), an unrecognized status string is rejected, a date range with `from` after `to` is rejected, and **at least one of query/status/date-range is required** (REQ-011's "search/filter by name, status, and date" implies a real criterion, not an unbounded dump of every Client/Matter). 9 domain tests (`SearchQueryTest`).
- Application (`application/search/SearchRepository`/`SearchService`): a new port interface returning a `SearchResult(List<Client> clients, List<Matter> matters)` — the first Search-specific application code; `SearchService` is single-repository as usual (unlike V0.5's cross-entity `MatterService`, Search doesn't need to orchestrate a business rule across entities, just fan out one query to two of them). 8 application tests against an in-memory fake, explicitly proving BR-007 (a Closed Matter matching the query is returned, not filtered out) and BR-008 (a match belonging to a different Firm is never returned) — not just the query/status/date-filter mechanics.
- Repository: **no new table** — SD-009 explicitly scopes this to existing `clients`/`matters` storage. This is also **the first native SQL (`nativeQuery = true`) in the Java codebase** — every prior `@Query` (`JpaDeadlineRepository`, `JpaDocumentRepository`) was JPQL; Postgres's `to_tsvector(...) @@ plainto_tsquery(...)` isn't expressible in JPQL. Added `search(...)` methods directly to the existing `JpaClientRepository`/`JpaMatterRepository` interfaces (reusing `ClientEntity`/`MatterEntity` — Spring Data JPA maps a `SELECT * FROM ...` native query straight back onto the mapped entity when the query returns all its columns, no manual row-mapping needed) rather than introducing a separate DAO. `plainto_tsquery` (not a hand-built `tsquery` string) was chosen deliberately: for name/title search, ANDing every word together is the *correct* behavior (typing "Meridian Buildtech" should require both words), unlike the `plainto_tsquery`-ANDs-everything problem CLAUDE.md already documents for V0.4's natural-language chat questions — that fix doesn't apply here and wasn't reapplied. Status is compared as `m.status::text = :status` to sidestep binding a plain Java `String` against Postgres's native `matter_status` enum column. Date-range boundaries are computed as `Instant`s in Java (`LocalDate.atStartOfDay(UTC)`) and bound directly against the `timestamptz` columns, **not** a Postgres `::date` CAST — the same timezone-sensitivity gotcha already in CLAUDE.md §4, avoided here on purpose rather than rediscovered. `ClientRepositoryImpl`/`MatterRepositoryImpl`'s private `toDomain(...)` mappers were loosened to package-private so the new `SearchRepositoryImpl` (same package) could reuse them instead of duplicating entity→domain mapping a third time.
- API: `GET /api/search?q=&status=&from=&to=` (all optional, at least one required) — `{ clients: ClientResponse[], matters: MatterResponse[] }`, matching System Architecture's pre-declared response shape exactly. `q`/`status`/date-range beyond the base `q` param are additive, not a spec deviation — REQ-011/AC-011 explicitly require status- and date-filtering, System Architecture's endpoint table just didn't spell out every query param.
- UI: a persistent search bar added to `NavBar` (plain `<form action="/search" method="GET">` — a real browser GET navigation, no client JS needed for the simplest possible reliable implementation) alongside Dashboard/Clients/Matters/Notifications; a new `/search` results page (SCR-14) — query echoed at top, results grouped by type (Clients, Matters) each showing name/title, status (Matters only — Clients have none), and a short "matched on" line, matching SCR-14's documented empty/error copy ("No results for '<query>' — check the spelling, or browse Clients/Matters directly", "Search failed — retry").

**Real environment note, not a new problem — the recurring one:** this machine's ~7.3GB RAM still requires starting Java and Next.js with constrained heaps (`-Xmx256m` / `--max-old-space-size=512`, CLAUDE.md §4) to run both together without OOM-ing; followed the now-established recovery procedure without incident this time.

**Live check, 2026-08-16, against the real 3-service stack + real Postgres:** created a real Client ("Vasquez Industrial Holdings") with two Matters under it, closed one of the two (no open Deadlines, so BR-003 didn't block it). `GET /api/search?q=Vasquez` returned the Client and **both** Matters — open and closed — confirming BR-007 live, not just in the fake. `GET /api/search?status=closed` alone (no query) correctly narrowed to closed Matters only; `GET /api/search?q=Vasquez&status=open` correctly combined both filters, dropping the closed Matter while still returning the Client. A date range excluding today returned nothing; the same range including today returned all three. `GET /api/search` with no params at all correctly returned `400 VALIDATION`; `status=archived` correctly returned `400` naming the bad value. Registered a second Lawyer/Firm and confirmed `GET /api/search?q=Vasquez` from that Firm returns `{ clients: [], matters: [] }` — real BR-008 isolation, not just the in-memory-fake test. On the UI side: fetched the real server-rendered `/search?q=Vasquez` page — query echoed, both group headings present, all three real records rendered with their "matched on" lines; the no-query and no-results empty states rendered their documented copy correctly; the search bar itself renders in the nav on the Dashboard. Re-fetched the same results page a second time (simulating a refresh) — identical real data both times, proving it's reading live Postgres state, not anything cached/mocked.

**Done (live action) — confirmed:** A lawyer types a Client or Matter name into the global search bar and lands on a results page that includes a match from a Closed Matter, which opens correctly in read-only mode (matches V0.5's already-verified Closed-Matter read-only behavior — Search only had to surface it, not re-verify BR-007's read access separately).

## Version 0.8 — Draft Generation from Templates

**Status:** Done — 2026-08-16

**Domain rule → repository → API → UI, together:**
- Domain rule (`domain/Template.java`): `create()` validates a non-blank name/body (firmId nullable — null means a system Template available to every Firm, a real value means Firm-custom, per System Architecture §3's ER note). `placeholders()` extracts distinct `{{name}}` references from the body; `render(fields)` is REQ-015's real rule — **every placeholder the body references must have a non-blank value or generation is refused, naming exactly which ones are missing** (a legal draft with a literal `"{{counterparty_name}}"` left in it is worse than refusing outright). `domain/Document.java` gained a parallel `createDraft(...)` factory (+ `NewDraftDocument`) alongside the existing upload-only `create()` — a generated draft's mime type is controlled internally, not REQ-003's upload allow-list, so it's validated separately rather than loosening that list. 25 new domain tests (`TemplateTest`, plus 5 new `DocumentTest` cases for `createDraft`).
- Application: `TemplateRepository`/`TemplateService` (new package, `application/template/`) — "available" Templates means system ones plus the caller's own Firm's custom ones, never another Firm's (BR-008's spirit applied to a nullable-tenant table). `DocumentRepository` gained a `createDraft(...)` method alongside `create()`. New `DraftGenerationService` (`application/document/`) mirrors `DocumentService.upload()`'s exact shape — validate (via `Template.render`) → store → create row → mark processing → trigger ingestion — reusing the same `StorageService`/`IngestionTrigger` ports V0.3 already established, not new infrastructure. 13 new application tests (5 `TemplateServiceTest`, 5 `DraftGenerationServiceTest`, plus the existing `DocumentServiceTest`'s fake updated for the new interface method) — explicitly proving BR-008 (a Firm can't list or generate from another Firm's custom Template) and that an unresolved placeholder is rejected *before* any storage I/O, same "validate before writing" ordering `DocumentService.upload` already uses for REQ-003.
- Repository: new `templates` table (migration `0007_foamy_beast.sql`) — `id, firm_id (nullable FK→firms), name, description (nullable), body, created_at`, matching System Architecture §3's declared shape exactly; `documents.source_template_id` (pre-staged since V0.3 but never wired up) now gets a real FK to it. **First native-adjacent addition here is actually JPQL, not native SQL** — `JpaTemplateRepository`'s "available" queries (`firm_id IS NULL OR firm_id = :firmId`) are plain `@Query` JPQL, following `JpaDeadlineRepository`'s existing subquery-join precedent, not a new pattern.
- API: `GET /api/templates` (→ `{ templates: TemplateResponse[] }`, each with a computed `placeholders: string[]` so the frontend never has to parse `body` itself), `POST /api/matters/:id/documents/generate` (→ `{ template_id, fields }` request, a bare `DocumentResponse` on success) — 201/400/404 exactly as System Architecture §4 declared; 502 reserved for `DraftGenerationService.DraftGenerationFailedException` (a real storage I/O failure), not exercised in the live check since storage didn't fail.
- UI: `generate-draft-modal.tsx` — a "Generate Document" button (exact label from UX doc's J5/nav-source note) next to Upload in the Documents section header; picking a template reveals one text input per placeholder, pre-filled from real Matter/Client data for the two placeholders named `client_name`/`matter_title` (the only field-to-data mapping the spec named via J5's example), left blank for the lawyer to fill in for everything else; a failed generation preserves entered edits (SCR-12's exact documented error behavior) rather than clearing the form. `documents-list.tsx` gained a "Draft" badge using the Design System's already-pre-declared Warning-badge variant (`--color-warning-*` — no new design-system work needed, it was anticipated before V0.8 started).

**A real, deliberate scope decision, not a shortcut discovered mid-build — flagged here rather than made silently:** neither Requirements nor System Architecture specifies what *format* a generated draft renders to. Building real DOCX or PDF generation would need a new document-authoring library (e.g. Apache POI/PDFBox) with no other justification yet in this codebase. Generated drafts are rendered as **plain UTF-8 text** (`.txt`, `text/plain`) instead — a real, correctly-formed file, not a mock, and one REQ-004's ingestion pipeline can already extract without any new parsing complexity or malformed-output risk. This did need one small Python addition: `extraction.py` had no `text/plain` branch at all (would have raised `Unsupported mime type` and marked every generated draft `failed`) — added a fourth `_extract_text` branch, same "no page concept, page_number=None" honesty already used for DOCX. Revisit if a lawyer-facing "download a properly formatted Word document" need becomes explicit — this was a real, visible corner cut made for velocity, not hidden.

**Live check, 2026-08-16, against the real 3-service stack + real Postgres, with real generated content flowing through the real ingestion pipeline:** `GET /api/templates` returned the two real seeded system Templates ("Non-Disclosure Agreement," "Demand Notice" — the exact name used in UX doc J5's own example) with correctly server-computed placeholder lists. Attempting generation with some fields missing correctly returned `400` naming exactly the missing ones (`effective_date, counterparty_name, matter_title, term_years, governing_law`). Generating with every field filled returned `201` with `isDraft: true`; polling `GET /api/documents/:id` a few seconds later showed the real ingestion pipeline had already carried it from `uploading` → `processing` → `ready`, and downloading it byte-for-byte confirmed every placeholder was correctly substituted with the real submitted values. [1]"`) whose citation pointed at the real generated Document by ID and filename — full proof of "becomes chat-queryable like any uploaded Document," not just that ingestion didn't crash. Verified BR-008 for Templates in both directions with a real second Firm: inserted a Firm-custom Template for it, confirmed the first Firm's `GET /api/templates` never listed it and a generation attempt against its ID returned `400 Template not found` (not a leak, not a 403 revealing it exists), then confirmed the second Firm's own session *could* see and would be able to use it.
