**Note on the "processing forever" bug (2026-08-15):** user reported a 60-page PDF upload appeared stuck on "Processing" for 5 minutes, resolving only after a manual tab refresh. **Note on the chunking/page-number rewrite (2026-08-15) — found by the user's own use of the AI Assistant, not a spike:** the user opened `document_chunks` in pgAdmin and reported the exact symptom set: `page_number` starting at 0, chunk 0 containing text from real pages 1–3, chunks breaking mid-word with no pattern, and `page_number` topping out at a value unrelated to the document's real page count. Root cause was three lines deep: `_extract_pdf` joined every page into one string before chunking (page boundaries destroyed), `chunk_text()` sliced that blob by raw character offset with no word/sentence awareness, and `save_chunks` stored the chunk's sequential index into the `page_number` column — the column never held a real page number at all. Rebuilt `app/domain/chunk.py` around a new `ExtractedPage`/`chunk_pages()` design: extraction returns text per real page; chunking runs per page (never spans two pages) and packs sentence-boundary segments (paragraph-aware where available, word-boundary hard-split only as a last resort for punctuation-free table rows) with whole-sentence overlap instead of a character slice. The user supplied a real fictional 11-page legal test PDF specifically for verifying this; used it both to write a realistic domain unit test (10 new tests) and for the live regression: `psql` confirmed `page_number` running 1→11 cleanly with zero cross-page mixing, and a live chat query about "Clause 7.2" returned a correctly-cited answer pointing at the real page containing it. | Domain-tested alone first (pure functions, no I/O), then re-verified end to end against the real 11-page PDF through the real 3-service pipeline — not just the unit tests. |
